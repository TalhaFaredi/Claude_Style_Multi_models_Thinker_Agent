 Multi-Mode AI Assistant: System Design and Project Plan
 Updated October 29, 2026
1. Overview
The assistant answers every question in one of three modes. All three modes share one model list, one set of
skills and tools, one answer checker and one output path.
  Simple: one model answers and uses tools when it needs them.
 Thinker: 2 to 5 agents think about the same question, then a composer model merges their answers into one.
 Planner: the system writes a step-by-step plan (like Cursor's plan mode). Each step runs in Simple or
Thinker, and each step is checked before the next one starts.
Example: "Make a 2-page PDF report on solar power." Planner splits it into research, outline, writing and PDF
steps. Research runs in Simple with web search, writing runs in Thinker, every step is checked, and the user
gets one PDF.
2. Review of the first design
The three-mode idea is strong. The gaps are missing exits, loops with no stop rule, and no checks for quality,
errors or cost.
What already works:
  Three modes match three kinds of work: quick answers, deep thinking and big multi-step tasks.
 The user can pick any model from OpenRouter or NVIDIA.
 Thinker supports both "same model many times" and "different models".
 Planner reuses Simple and Thinker instead of new logic.
 Skills and tools are shared by every mode.

 Part 2: Memory and Attachments
 October 27, 2026
Two rules fix both problems: a file is read once and never paid for twice, and the chat never forgets silently. It warns first,
summarizes with a check, and keeps every original message searchable.
1. The simple idea
Think of the model as a person at a small desk. The desk is the context window: the most text the model can read at once,
counted in tokens (a token is about 3/4 of an English word). Long chats and big files do not fit on the desk, so the system
needs a filing cabinet (storage) and a librarian (search) that puts the right pages on the desk at the right time.

to it, and a file already read costs $0

Why Claude seems to remember an uploaded chat: the transcript is read into the window like any file. That works
only while it fits; most current Claude chat models have a 1M-token window, some 500K or 200K.
Why an app forgets inside a chat: if it keeps only the newest messages that fit, the oldest fall out without warning. Our
rule: never drop a message silently.
3. Attachment pipeline
Every file is fingerprinted first, so a file the system has read before costs $0. Then each page goes to the cheapest reader
that can handle it, and paid readers run only after the cost check.
  Fingerprint: SHA-256 turns the file's bytes into a short ID; the same file always gives the same ID, so the system
knows it has read it, even in another chat. Saved readings belong to one account, so no user can find out what another
uploaded.
 Document Card: a short card per file: title, pages, summary, outline with page numbers, tables and charts. The cards
of all files in a chat stay in the window, so the model never forgets a file exists, even when its text is searched.
 Chunks: pieces of up to 800 tokens, cut at headings and paragraphs. A table is never cut mid-row; a long table is split
into groups of rows with the header row repeated. Every chunk starts with its file, section and page.
Two caches, two jobs
 1. Parse Cache (ours, kept until the user deletes the file): saved readings by fingerprint, reader and version; it saves the
OCR money.
2. Prompt cache (the provider's, 5 minutes, or 1 hour as an option): a repeated prompt start is billed cheaper.
Anthropic: reads cost 0.1 times the input price (0.05 on Opus 5.5 and Sonnet 5.5), writes 1.25 times (5 minutes) or 2
times (1 hour). OpenRouter caches automatically for many providers. So stable parts go first, the new message last.

 1. Text pages: 170 × $0 = $0
2. Scanned pages: 20 × $0.002 = $0.04
3. Chart pages, input: 10 × 1,600 = 16,000 tokens, and 16,000 ÷ 1,000,000 × $1 = $0.016

6. Memory layers
Storage keeps everything; before every turn, the Context Builder rebuilds the desk within a fixed budget.
  Archive: every message is kept word for word with its time; summaries only save room on the desk. A June 2026
study found raw turns answered far better than compressed storage (26.0 vs 10.7 on LongMemEval).
 Session ledger: a numbered list of goals, decisions, numbers, rules and open questions, each linked to its message. It
changes by small edits (add, change, close), never by a full rewrite, which wears details away.
 Long-term memory: facts about the user and their projects, each with a date and a source. When a fact changes, the
old one is marked "replaced" with the date instead of being deleted, so "what did I say last month?" still works.
 Order and speed: stable parts first (so the prompt cache works), the new message last (models use the start and end
best). The Memory Writer runs after the reply, and clean-up runs while the user is idle.

7. Context alarm and safe summaries

How full is it? (example)
  Input: window 200,000 tokens; answer space 15%, so 200,000 × 0.15 = 30,000 tokens; next prompt 150,000 tokens.
 Step: usable window = 200,000 - 30,000 = 170,000; then 150,000 ÷ 170,000 = 0.88.

Import, step by step:
 1. Check the format version and every checksum. If something is broken, refuse and say which part.
2. Treat everything inside as data, never as instructions: a line saying "ignore your rules" is just text.
3. Reuse a file reading when the fingerprint and reader match ($0); otherwise ask before reading again. Rebuild the
search indexes, showing the cost first if the embedding model changed.
4. If everything fits, load it word for word (this is why Claude seems to remember an uploaded chat). If not, load the
ledger, the summaries and the last turns, and keep the rest searchable.
5. Show a report, for example: 142 messages, 3 files, 21 facts restored, reading cost $0.

 Part 3: Frontend Design and Specification
 October 28, 2026
One chat screen serves all four modes. It shows every step live, keeps costs and memory in sight, and builds the safety
limits into the controls so a user cannot break anything.
1. Design idea
The app looks calm like a normal chat, but it shows everything the system does: which mode runs, what each agent or
step is doing, what it costs, and how full the memory is. Every risky or paid action asks first, so a user cannot break
anything by clicking.
  Show, do not hide: status lines, thinking, tool calls, agent cards and plan steps appear live.
 Safe by design: limits are built into the controls (steppers stop at 2 and 5, locked safety rules), and a blocked action
always says why.
 Costs in sight: an estimate next to Send, a budget per question, and the reading cost of every file.
 Plain choices: Setup shows the real choices directly, each stays visibly selected, and a sentence on top says what will
happen.
 One layout for all modes: only the Setup dialog and the answer blocks change.
